## 1. Qwen3-30B-A3B 的结构

| 维度 | 取值 |
|---|---|
| 架构 / model_type | `Qwen3MoeForCausalLM` / `qwen3_moe` |
| 总参数 / 激活参数 | ~30B / ~3B（A3B，稀疏 MoE） |
| hidden_size | 2048 |
| num_hidden_layers | 48 |
| 注意力 | 32 heads，4 KV heads（GQA），head_dim=128 |
| MoE | num_experts=128，num_experts_per_tok=8（top-8 路由），moe_intermediate_size=768 |

结构要点：

- **每层都是 MoE 层**，没有顶层稠密 `mlp.up_proj/down_proj`。
- 每层 MLP = 128 个专家 `mlp.experts.{0..127}.{gate_proj,up_proj,down_proj}`（各 768×2048 / 2048×768）+ 一个路由器 `mlp.gate`（`Qwen3MoeTopKRouter`，其 `weight` 是 `nn.Parameter`，形状 128×2048）。
- 权重索引共 18867 个 key；本地 checkpoint 是**逐专家**布局的分片 safetensors。
- transformers 5.9.0 里 `Qwen3MoeSparseMoeBlock` 已被重构为「融合 3D 专家权重」（`Qwen3MoeExperts`，`gate_up_proj`/`down_proj` 变成 `nn.Parameter`），与本地逐专家 checkpoint 不一致——这是适配的根源问题之一。

## 2. 量化 Qwen3-MoE 的技术难点

1. **资源门槛高**：30B fp16 约 60GB+ 内存（实测 CPU RSS 峰值 ~63GB）；逐层搬 GPU 时单层含 128×768 的 MoE 也很大，需 `--save_per_layer`、减小 `--nsamples` 控制峰值。
2. **框架原本只认稠密结构**：`get_named_linears(layer, nn.Linear)` 假设稠密；融合后的专家不是 `nn.Linear`，找不到专家投影；`cache_name` 无 MoE 条目（误落到 `qwen3`）。
3. **norm fusion 破坏路由（最隐蔽）**：守卫 `if 'qwen3.' not in args.net.lower()` 对 `qwen3-30b-a3b` 判断失败，导致 `post_attention_layernorm` 被折叠进 128 个专家的 `up_proj/gate_proj` 并把 norm 置 1；但路由器 `mlp.gate` 是 `nn.Parameter` 没被折叠 → 路由器与专家看到不同输入 → top-k 选错专家 → 校准/量化/评估全错。
4. **专家激活稀疏**：每 token 只激活 top-8 专家；老代码 hook 固定 `experts.0/experts.1.up_proj` 取激活统计，若专家 0/1 未被路由就 `KeyError`。
5. **参数量爆炸**：每层 128 专家 × 3 投影 = 384 个投影；若照搬 dense 每个投影独立旋转+缩放矩阵，光旋转/缩放就 `128×3×4=1536` 个参数/层。
6. **逐专家 vs 融合布局版本冲突**：5.9.0 融合布局与本地逐专家 checkpoint 无法原样 load_state_dict。
7. **Stage2 格点搜索慢**：128 专家时每个专家投影 ~15–20s，单层约 1.5–2h。
8. **评估侧部分量化加载**：只量化部分层时，`load_quantized_model(load_per_layer=True)` 会遍历 48 层找 `layer{i}.pth`，未量化层无文件会报错。

## 3. 当前技术方案

### 第一轮——逐专家布局猴子补丁（适配根基）

- 新增 `LiftQuant/models/qwen3_moe_per_expert.py`：`PerExpertQwen3MoeSparseMoeBlock` 用 `Qwen3MoeMLP` + `Qwen3MoeTopKRouter` 把融合 block 改回 `nn.ModuleList[Qwen3MoeMLP]`（`experts = nn.ModuleList([...])`），forward 用 Mixtral 式逐专家稀疏循环；`patch_qwen3_moe_per_expert()` 在 `from_pretrained` 前替换 `Qwen3MoeSparseMoeBlock`。
- `LMClass.py` 加载前调用 patch；`liftq.py` 顶部新增 `is_moe`（按 `model_type/architectures` 判断，不再只看目录名）。

### 第二轮——加载/评估路径 + norm fusion 守卫

- `e2e_utils.py` 加 `_is_qwen3_moe`、`from_config` 前 patch、重写 `auto_mix_precision` 的 `expc_choice`（llama-3 之外回退统一 expc）。
- `main.py` 的 `cache_name` 命中 `qwen3-moe`。
- `liftq.py` norm fusion 改为 `if is_moe: skip`。
- `stage_training.py` 的 `_build_worker_qlayer` 重建层前也 patch，保证 DDP worker 结构一致。

### 第三轮——GPU 实跑验证

- layer0 全流程跑通（无 OOM/KeyError）。

### 第四轮——MoE 专家分组旋转矩阵（核心创新）

- 新增 `MoeSharedRotScale`（组级共享容器，持有 `Trans/a1/a2`），挂在 `mlp.moe_shared.{g}.{gate,up,down}_proj` 上，state_dict 只存一份。
- 每个专家 `TmpLinear`/`FWTLinear` 用 `object.__setattr__` **引用**共享对象（避免重复注册导致 `named_parameters()/state_dict` 重复）。
- **组级共享**旋转/缩放矩阵（`Trans/a1/a2`），**逐专家**保留 quant 参数（`quantizer.scale/alpha`、`weight/scale/maxq/root/packed_weight`）。
- `--moe_num_groups` 控制组数（默认 1）；`a1` 初始化用「被路由最多专家」的 `up_proj` std 统计（down 置 1）；q/k/v/o 保持 dense 行为。
- 共享物化只做一次（`to_buffer()`、`M@linear_right`、`a2.repeat_interleave` 按 group/proj_type 各执行一次），避免 128 个专家重复触发 `AttributeError` 和语义错乱；参数收集按 `id()` 去重避免 AdamW duplicate。
- Stage1→Stage2 转换 + `pack_to_int8`；DDP 下 Stage2 格点搜索跨 rank 分片。
- 评估侧 `e2e_utils.py` 新增 `_get_moe_group_count` / `_replace_moe_layer_for_eval`，从 checkpoint 推断组数、分组重建结构。

## 4. 实验结果

### 4.1 冒烟 / 结构正确性

- patch 后 `from_config(meta)`：layer0.mlp 的 key 为 `experts.{0..127}.gate/up/down_proj.weight` + `gate.weight`，共 385 key；全模型 18867 key 与权重索引 **missing=0 / unexpected=0**。
- `PerExpertQwen3MoeSparseMoeBlock.forward` 与融合参考实现 **max abs diff = 0.0**。
- 分组后 layer0 checkpoint：`moe_shared` 12 个 key（1 组 × 3 投影 × {a1,a2,Trans.linear_left,Trans.linear_right}）；`packed_weight` 388（4 注意力 + 384 专家）；**旋转+缩放从 1536 降到 12，节省 128×**。

### 4.2 实际量化规模

- 已量化 **26 层（layer 0–25）**，配置 `wbits=2, expc=24to8, moe_num_groups=4`，每层 packed 约 236MB（`non_layer.pth` 1.24GB）；层 26–47 仍为 FP（即当前是**部分量化**）。
- 评估：FP 基线 vs LiftQuant（26 层量化），`--limit 300`、12 个任务，bfloat16、batch=8。

### 4.3 精度对比（limit=300）

| 任务 | FP 基线 | LiftQuant(26层量化) | 差异 |
|---|---|---|---|
| mmlu acc | 0.8295 | 0.8232 | -0.006 |
| lambada_openai acc | 0.7167 | 0.6900 | -0.027 |
| lambada perplexity | 3.157 | 3.493 | +0.34 |
| hellaswag acc_norm | 0.6900 | 0.6500 | -0.040 |
| winogrande acc | 0.7200 | 0.7400 | +0.020 |
| piqa acc_norm | 0.8367 | 0.8333 | -0.003 |
| truthfulqa_mc1 acc | 0.4100 | 0.4200 | +0.010 |
| truthfulqa_mc2 acc | 0.6003 | 0.5915 | -0.009 |
| openbookqa acc_norm | 0.4567 | 0.4700 | +0.013 |
| boolq acc | 0.8900 | 0.8867 | -0.003 |
| rte acc | 0.7653 | 0.7617 | -0.004 |
| arc_easy acc_norm | 0.8467 | 0.8333 | -0.013 |
| arc_challenge acc_norm | 0.6133 | 0.6367 | +0.023 |

**结论**：量化后整体与 FP 基本持平（多数任务在 ±0.01~0.04 内，部分任务如 winogrande/openbookqa/arc_challenge 甚至略高），考虑到 limit=300 的噪声，可以认为当前 26 层量化**精度损失很小**，方案可行。
